# WorkFlow

Учебный интерфейс системы поддержки на Nuxt 4. Для этого этапа используются локальные Nuxt API-маршруты: они имитируют backend и позволяют проверить запросы, фильтрацию и сетевые состояния без внешнего сервера.

## Запуск

```bash
npm install
npm run dev
```

Откройте адрес, который покажет Nuxt (обычно `http://localhost:3000`).

## Проверка и сборка

```bash
npm run build
npm run preview
```

Для статической сборки используйте `npm run generate`. Чтобы загрузить проект в свой GitHub-репозиторий, создайте пустой репозиторий и выполните из папки проекта:

```bash
git init
git add .
git commit -m "Create WorkFlow Nuxt app"
git branch -M main
git remote add origin https://github.com/<ваш-логин>/<имя-репозитория>.git
git push -u origin main
```

## API

Реализованы `GET /api/requests`, `GET /api/requests/:id`, `GET /api/users`, `GET /api/customers` и `GET /api/categories`. Создание заявки использует `POST /api/requests`. Данные моковые и сбрасываются при перезапуске сервера.

Фильтры и страница хранятся в URL: `q`, `status`, `priority`, `assignee`, `sort`, `page`. Например:

```text
/requests?q=CRM&status=Новая&sort=oldest&page=1
```

Для проверки сетевых состояний:

- `/requests?delay=1500` — медленный ответ и skeleton;
- `/requests?demo=empty` — пустой ответ;
- `/requests?demo=429` или `/requests?demo=500` — ошибка API; повторите запрос кнопкой на странице.

Эти параметры предназначены только для демонстрации локального mock API.

## Структура стилей

`app/assets/css/main.css` подключает тематические файлы: базовые токены и сброс, layout, общие компоненты, страницы, адаптивность и дополнительные состояния. Стили можно менять в соответствующем разделе, не складывая всё в один файл.

## Состояние и взаимодействия

- **Server state:** заявки, их версия, история и комментарии хранятся через mock API. Для изменения заявки используется `PATCH /api/requests/:id`, для комментариев — `POST /api/requests/:id/comments`.
- **URL state:** поиск, фильтры, сортировка и страница остаются в query-параметрах `/requests`.
- **Local state:** открытие меню/формы, введённый комментарий и незавершённый ввод живут в компоненте.
- **App state:** Pinia store `requestUi` содержит только уведомление и отмену последнего изменения статуса/приоритета; store `preferences` содержит настройку плотности списка.
- Настройка плотности сохраняется в `localStorage` и применяется к спискам, статистике и карточкам.
- Приоритет и статус обновляются оптимистично. На 409/500 прежнее значение восстанавливается, а сообщение объясняет причину. Последнее изменение статуса или приоритета можно отменить кнопкой «Отменить изменение».

Для проверки rollback откройте `/requests/1042?demoUpdate=409` или `/requests/1042?demoUpdate=500` и измените статус/приоритет. Чтобы проверить ошибку комментария, используйте `/requests/1042?demoComment=500`.

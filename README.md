# WorkFlow

WorkFlow — приложение для работы с заявками на Nuxt 4, Nitro и PostgreSQL. При первом обращении сервер создаёт схему базы данных, а команда заполнения добавляет локальные демонстрационные учётные записи и заявки.

## Локальный запуск

Необходимы Node.js 20.6 или новее, npm и Docker Compose. Перед запуском убедитесь, что Docker Desktop или OrbStack запущен.

```bash
npm install
cp .env.example .env
npm run db:up
docker compose ps
npm run db:seed
npm run dev
```

Перед запуском `db:seed` дождитесь, чтобы сервис `postgres` в `docker compose ps` имел состояние `healthy`. Откройте адрес, который выведет Nuxt (обычно `http://localhost:3000`). Строка подключения в `.env.example` соответствует локальным настройкам из `docker-compose.yml`.

Администратор, оператор и исполнители создаются командой заполнения базы. Клиент может зарегистрироваться на странице `/register`. Демонстрационные учётные записи:

| Роль          | Электронная почта                | Пароль         |
| ------------- | -------------------------------- | -------------- |
| Администратор | `admin@workflow.local`           | `Admin123!`    |
| Оператор      | `operator@workflow.local`        | `Operator123!` |
| Исполнитель   | `agent.brungilda@workflow.local` | `Agent123!`    |
| Клиент        | `client1@workflow.local`         | `Client123!`   |

Чтобы задать свои пароли для локальных демо-учётных записей, укажите переменные `WORKFLOW_ADMIN_PASSWORD`, `WORKFLOW_OPERATOR_PASSWORD`, `WORKFLOW_AGENT_PASSWORD` и/или `WORKFLOW_CLIENT_PASSWORD` перед выполнением `npm run db:seed`. Заполнение базы запрещено при `NODE_ENV=production`.

Команда `npm run db:down` останавливает локальную базу, не удаляя её том с данными. Не используйте демонстрационные пароли и учётные записи в открытом или рабочем окружении.

## Как проверить приложение вручную

### Проверка интерфейса

1. Зарегистрируйте клиента на `/register` либо войдите под `operator@workflow.local` и паролем `Operator123!`.
2. Откройте «Заявки»: должны отображаться заявки из PostgreSQL. Проверьте поиск, фильтры, сортировку и переход по страницам.
3. Откройте заявку, измените статус или приоритет, добавьте комментарий и обновите страницу — изменения должны сохраниться.
4. Откройте меню профиля и выйдите. Закрытая рабочая страница должна перенаправить на вход. Для проверки экрана повторного входа откройте `http://localhost:3000/login?reason=session-expired`.
5. Войдите под `client1@workflow.local` / `Client123!`: клиент должен видеть только свои заявки.
6. Войдите под `agent.brungilda@workflow.local` / `Agent123!`: исполнитель должен видеть только назначенные ему заявки.
7. Проверьте адаптивность в инструментах разработчика браузера на ширине 360, 768 и 1280 пикселей.
8. Войдите как администратор и откройте `http://localhost:3000/admin`. Затем выйдите, войдите как клиент и откройте этот же адрес — появится экран `403`.
9. На странице заявки под оператором попробуйте назначить исполнителя; под исполнителем запросите информацию или зафиксируйте решение. Для перехода в ожидание или решение введите обязательную причину.

### Проверка доступа по ролям в браузере

- Клиенту доступны только его заявки. Для проверки чужой заявки войдите как `client1@workflow.local` и откройте `http://localhost:3000/requests/1041` — заявка не должна раскрыть данные.
- Исполнитель видит только назначенные ему обращения. Войдите как `agent.brungilda@workflow.local` и откройте `http://localhost:3000/requests`.
- Клиент не может открыть административную страницу: `http://localhost:3000/admin` должен показать экран `403`.
- После выхода откройте `http://localhost:3000/requests` — приложение должно перенаправить на страницу входа.
- Для просмотра ответа списка в формате JSON откройте `http://localhost:3000/api/requests` после входа. Без входа API вернёт `401`.
- Оператор и администратор могут увидеть деактивированного исполнителя в окне назначения. Попытка назначить его должна показать сообщение об ошибке; сервер не сохранит такое назначение.

## API

Для приватных маршрутов требуется сессионная cookie `workflow_session` с флагом `HttpOnly`.

- `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/session`
- `GET /api/requests`, `POST /api/requests`
- `GET /api/requests/:id`, `PATCH /api/requests/:id`
- `GET /api/requests/:id/comments`, `POST /api/requests/:id/comments`
- `GET /api/users`; `PATCH /api/users/:id` (только администратор)
- `GET /api/customers`, `GET /api/categories`

Список заявок принимает параметры `q`, `status`, `priority`, `assignee`, `sort`, `page` и `pageSize`; интерфейс хранит фильтры в URL. Сервер проверяет входные данные и права для защищённых операций. Клиент видит и комментирует только собственные заявки, исполнитель видит назначенные ему заявки и может менять их статус, оператор и администратор управляют заявками. Изменять роли и активность пользователей может только администратор. Назначать можно только активных пользователей с ролью исполнителя.

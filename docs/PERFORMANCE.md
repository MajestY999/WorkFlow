# SSR, SEO и performance

## Режим рендеринга

Лендинг (`/`), FAQ (`/faq`), центр помощи (`/help`), категории, список
инструкций и статьи (`/articles/**`) отдаются через Nuxt SSR. Тексты и данные
страниц доступны в первом HTML; поиск фильтрует уже загруженные данные на
клиенте. Публичные маршруты не запрашивают сессию и не требуют доступности
PostgreSQL.

Для этих маршрутов не добавлены `routeRules`: содержимое небольшое, а
canonical URL и sitemap строятся с учётом origin запроса. Кеширование SSR
ответов по пути могло бы смешать canonical URL разных доменов. `robots.txt` и
`sitemap.xml` кешируются на час. Для стабильного production origin задайте
`NUXT_PUBLIC_SITE_URL` (например, `https://workflow.example`).

В статьях и категориях используется явный HTTP 404 при неизвестном slug;
страница ошибки не индексируется. Уникальные title, description, canonical и
Open Graph title/description/type/url задаются на странице. Sitemap включает
лендинг, FAQ, центр помощи, список статей, три категории и пять статей.

## Методика и результаты

Сравнение выполнено на одной машине и одной версии Node: production-сборка
исходной ревизии `HEAD` и production-сборка после изменений. Серверы запущены
через `node .output/server/index.mjs`; TTFB — медиана 10 последовательных
тёплых запросов `curl` на localhost. Размер HTML — тело ответа. JS/CSS
измерены как единственный начальный asset соответствующего типа; gzip — размер
локального gzip-сжатия файла, без учёта HTTP-заголовков. Это локальный
сравнительный замер, а не полевой Core Web Vitals.

| Маршрут                          | До: статус / TTFB / HTML              | После: статус / TTFB / HTML |
| -------------------------------- | ------------------------------------- | --------------------------- |
| `/`                              | 200 / 1,3 мс / 4 385 B                | 200 / 1,6 мс / 5 084 B      |
| `/faq`                           | 302 на вход, содержимого страницы нет | 200 / 1,4 мс / 5 179 B      |
| `/help`                          | 302 на вход, содержимого страницы нет | 200 / 1,4 мс / 5 906 B      |
| `/articles`                      | 302 на вход, содержимого страницы нет | 200 / 1,4 мс / 5 862 B      |
| `/articles/create-first-request` | 302 на вход, содержимого страницы нет | 200 / 1,1 мс / 5 510 B      |

| Начальные ресурсы |                       До |                    После |
| ----------------- | -----------------------: | -----------------------: |
| JavaScript        | 81 826 B (29 843 B gzip) | 88 797 B (32 188 B gzip) |
| CSS               |  25 750 B (6 465 B gzip) |  30 664 B (7 149 B gzip) |

До изменений middleware перенаправлял публичные адреса на вход, поэтому их
контент и SEO metadata не были доступны поисковому роботу. После изменений
страницы возвращают содержательный HTML и корректный статус 200; неизвестная
статья возвращает 404. Тёплый TTFB проверенных страниц после изменений —
1,1–1,6 мс на localhost.

## Performance budget

Бюджет для production-сборки:

| Метрика                     |   Бюджет |           Результат |
| --------------------------- | -------: | ------------------: |
| Тёплый localhost TTFB (p50) | ≤ 100 мс |          1,1–1,6 мс |
| SSR HTML публичной страницы | ≤ 12 KiB |    максимум 5 906 B |
| Начальный JavaScript, gzip  | ≤ 35 KiB | 32 188 B (31,4 KiB) |
| Начальный CSS, gzip         | ≤ 10 KiB |   7 149 B (7,0 KiB) |

Размеры начальных JS и CSS выросли относительно исходной сборки: публичные
маршруты, поиск, навигация и metadata добавили 2,3 KiB gzip к JS и 0,7 KiB
gzip к CSS. Это измеримый компромисс за требуемый SSR-first функционал; оба
ресурса остаются в заданном бюджете.

## Принятые оптимизации

- SSR для публичных страниц вместо клиентского получения основного содержимого:
  поисковик и пользователь сразу получают текст и metadata.
- Пропуск проверки сессии на публичных маршрутах: убирает лишний запрос к API
  при рендеринге FAQ/справки и предотвращает ошибочный redirect на вход.
- Статические данные страниц без runtime API-запросов: не блокируют первый HTML
  и уменьшают зависимость публичного контента от базы данных.
- Удалён внешний Google Fonts `@import`; используется системный sans-serif стек,
  поэтому первый рендер не зависит от стороннего font CSS и сетевого запроса.
- В выбранных макетах нет изображений, поэтому изображения и lazy loading не
  добавлялись.
- `robots.txt` и sitemap доступны как отдельные ответы и кешируются на час.
  Sitemap генерируется из тех же данных, что и страницы статей/категорий.
- Даты заявок форматируются в явно заданном UTC. Раньше часовой пояс по
  умолчанию мог отличаться на сервере и в браузере и давать hydration mismatch.
  Регрессионный unit-тест проверяет форматирование при `America/Los_Angeles`.

Проверка production UI в браузере: целевые маршруты содержат SSR `<main>`,
неизвестная статья имеет статус 404, предупреждений hydration нет; при ширине
360 px горизонтального переполнения нет. Полевые LCP/CLS и результаты
Lighthouse не измерялись; локальный TTFB не следует считать заменой таких
измерений.
